# ADR-008: Adoption is a reusable workflow with its own failing job, checked in two layers

Date: 2026-10-30
Status: Accepted

## Context

Story #124, raised by GoServe (feedback issue #124): the project carried the `knowledge/shipquick_latest`
submodule for 19 days with zero checks wired, and nobody noticed. ShipQuick only shipped a reusable
workflow for the roadmap page; every other check (`check_block.py`, `check_closes.py`,
`check_frontend_design.sh`, `check_uat.py`, `check_environments.sh`) lived only in ShipQuick's own
`ci.yml`, with nothing forcing a child to copy the equivalent jobs itself. `adopt.sh` wrote
`.pre-commit-config.yaml` only when the child had none, so a child that already had any
pre-commit config kept it untouched and silently lacked the ShipQuick hooks.

## Decision

- `.github/workflows/checks.yml` is a new reusable workflow (`workflow_call`) carrying every PR
  gate a child needs, as separate jobs: `adoption`, `team-block`, `frontend-design`, `uat-on-main`,
  `environments`. It is the single source of truth for what "wired checks" means; `ci.yml` and
  `checks.yml` now share the same check scripts (duplication is in job boilerplate only, not logic).
- `adopt.sh` writes `.github/workflows/shipquick-call.yml`, the caller, pinned to the exact commit
  of the `knowledge/shipquick_latest` submodule — the same pattern already used for
  `roadmap-call.yml`. `.github/workflows/shipquick-call.yml` in ShipQuick's own repo is the
  template adopt.sh reads from, kept inert (`workflow_dispatch` only) because ShipQuick carries no
  submodule of its own and would always fail the `adoption` job if it called itself for real.
- The `adoption` job runs first and fails loudly, naming the fix, when the caller's pin does not
  equal the submodule's actual commit, or `.pre-commit-config.yaml` carries no ShipQuick hooks.
  `adopt.sh --check` prints the same verdict locally, before a commit ever reaches GitHub.
- A second layer catches the case layer 1 cannot: a child with no caller at all has no CI of its
  own to fail. `docs/children.md` is the registry; `scripts/adoption_scan.py`, run daily
  (`.github/workflows/adoption-scan.yml`), opens one `feedback` issue in ShipQuick itself for any
  child whose default branch lacks the caller, or pins a ShipQuick commit over 14 days old.

## Consequences

Good:

- A child cannot silently carry ShipQuick without its checks running: either its own CI fails
  (layer 1), or ShipQuick notices from the outside within a day (layer 2).
- One reusable workflow means a new check added to `ci.yml` and `checks.yml` together is the only
  way to add a gate; nobody can add a check that only protects ShipQuick's own PRs.

Bad and to watch:

- `docs/children.md` must be kept current by hand (or by a future story); a child never added to
  it is invisible to layer 2 until someone adds it.
- The 14-day staleness window and the `D1` milestone default baked into the `environments` job in
  `checks.yml` are both judgment calls, not something the issue pinned down exactly; revisit if a
  real child's cadence does not fit either number.
