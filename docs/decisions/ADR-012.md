# ADR-012: Library first, native with a shared feel

Date: 2026-11-09
Status: Accepted (owner approved the plan, 9 Nov 2026, story #181)

## Context

GoServe's UI was slow to build. No UI library was picked, so every component was hand-made.
GoServe is a PWA today. It will soon be a native Android app and a native iOS app.
The owner wants both apps to feel the same. The look may differ a little.

The owner's rules (9 Nov 2026):
- Take a library fully. Customise it lightly. Never hand-write UI.
- A custom component is built only after the owner says yes.
- Study Meta's Astryx. Use its components where we can. Where we cannot, copy its whole agent architecture.

This is generic for every ShipQuick child. GoServe is only the first user.
Plan: `docs/plans/2026-11-09-library-first.md` (PR #193).

## Options

| | (a) Compose M3 + SwiftUI + shared tokens | (b) Compose Multiplatform | (c) Meta Astryx |
|---|---|---|---|
| What it is | Google's Android library, Apple's iOS components | JetBrains: the same Material code on both | Meta's React web design system (MIT, beta 0.7.11) |
| Native Android | Yes, full | Yes, full | Nothing |
| Native iOS | Yes, Apple native | Material drawn on iOS; looks like Android, 9 MB+ bigger | Canary only, 6 SwiftUI parts, "not for production" |
| Web | No | No | Yes: 150+ components, 58 page templates |
| Agent support | We build it | We build it | Best seen: lookup CLI, a doc file per component, managed AGENTS.md block, MCP, llms.txt |
| Blocks custom UI | detekt, Konsist, SwiftLint | detekt | Its lint is private; `doctor --built` only warns |

Research 9 Nov 2026, Tier A (the vendors' own repos and docs).
Astryx is truly Meta's (0.95). Its agent support is the best of the three, but only on the web (0.85).

## Decision

**(a) for native. (c) used directly on the web only. (c)'s agent architecture copied for all three platforms. (b) dropped.**

1. **Android** uses Jetpack Compose Material 3 directly (`Button`, `TextField`, `NavigationBar` and the rest).
   No ShipQuick wrapper rewrites them. Our brand goes in through `MaterialTheme`, generated from `design/tokens.json`.
2. **iOS** uses SwiftUI's standard controls directly. Our brand goes in through `Tokens.swift`, never a restyled copy.
3. **Web** children use `@astryxdesign/core` directly, pinned to an exact version. The theme uses Astryx's own `defineTheme`.
   CI runs `astryx doctor --built` as a failing check. Beta risk: the pin, plus a monthly look at its release notes.
4. **Compose Multiplatform is dropped.** It draws Material on iOS. The iOS app would look like Android and grow 9 MB or more.
   That breaks "native, with a shared feel".
5. **One tokens file** gives both apps the same feel: colour, type, spacing, shape, motion, haptics, touch-target size.
6. **Astryx's agent architecture is taken as code, never rewritten.** Its doc schema and contract types are copied (S2).
   Its CLI is used as shipped, pinned, never copied (S3, see "What the CLI serves"): our integration points it at our docs,
   adds the Compose and SwiftUI words to its managed agent block, and `scripts/ui.sh` fails where the CLI only warns.
   Its doc guards, two-tier lint and vibe tests are copied as their stories land.

## MIT copy policy

- Every copied file keeps its header: `Copyright (c) Meta Platforms, Inc. and affiliates.` and the MIT notice.
- The upstream commit is recorded next to the copy (`ui/UPSTREAM.md`, story S3).
- A swizzled Compose M3 component keeps its Apache 2.0 header the same way.
- We never call our product "Astryx". The name is Meta's.

## Consequences

- New CLAUDE.md rule 38, "Library first". Full rule: `docs/COMPONENT_LIBRARY.md`.
- A custom component needs a `component-request` (`docs/templates/component-request.md`) and the owner's yes.
  The yes counts only as an issue comment by a reviewer account, plus the `component-approved` label. Story S8 (#186) checks it.
- On Android and iOS, third-party UI kits are banned. The web uses Astryx.
- The Android and iOS libraries live inside the kit (see "Where it lives" below). They hold no brand or client data.
- This story writes the rule only. Stories S2 to S11 build the schema, the CLI, the repos, the lint and the gates.
  Until they land, the rule is enforced by review.
- This closes the library pick in story #133.

## Where it lives (owner, 9 Nov 2026: "haan theek hai")

The first plan put Android and iOS in two new repos. That changed the same day.

**Decision.** Both libraries live inside the kit, as folders:
- `ui/android/`: a Gradle build. A child uses it with `includeBuild("knowledge/shipquick_latest/ui/android")`.
- `ui/ios/`: an SPM package. A child uses it with `.package(path: "knowledge/shipquick_latest/ui/ios")`.

**Why.**
- Parity in one PR. A contract change, its Android code and its iOS code land together, or not at all.
  With two repos, one side can lag and the drift test runs too late.
- No extra submodules. The kit is already a submodule in every child. Two more pins would mean two more bumps to forget.
- It is how Astryx does it: one repo, many platforms.

**Cost.** The kit grows. So the Android and iOS CI jobs run only when `ui/android/**` or `ui/ios/**` change,
each with a timeout. The macOS runner is free, because the kit is public.

The empty repos `satvik-jain-iitd/shipquick-ui-android` and `satvik-jain-iitd/shipquick-ui-ios` are not used.
Archiving or deleting them is the owner's call.

## What the CLI serves (story #183, 9 Nov 2026; three spikes run by the owner)

The plan said to copy Astryx's CLI into `ui/cli/`. It is 3314 files (27 MB) and pulls in babel, jscodeshift
and stylex. So we **use the CLI as shipped**, pinned, and plug in through its own extension points. That is
closer to rule 38 ("take it fully, never hand-write") than a 700-file copy we would have to keep in step.

- **Where:** `ui/tool/` is a dev-only package: `@astryxdesign/cli` and `@astryxdesign/core` at exactly
  `0.7.11` (the latest stable; `0.7.12` is canary only), and core's peers `react`/`react-dom` `19.3.1` and
  `@stylexjs/stylex` `0.19.1`. Exact pins plus the lockfile npm wrote. Install with `npm ci --ignore-scripts`.
  No app ever ships these. A native child only runs `ui`.
- **Why core is installed:** spike 1 showed the CLI stops with `ERR_CORE_NOT_FOUND` without it, even for docs.
- **Web children:** the CLI as shipped, with core's own component docs. Our integration adds no web component,
  so nothing clashes with core (spike 2: two `Button`s made `--dense` refuse).
- **Android and iOS:** the CLI's `component` command needs a React source file beside each doc (spike 2:
  "missing its same-stem source file Button.tsx"). A stub `.tsx` would be hand-written filler, so never.
  Native parts are **reference topics** in `ui/integration/docs/` (`ui docs android-button --dense`),
  generated by `scripts/ui_topics.py` from `ui/components/`. S2's `check_ui_docs.py` still checks that source.
  Spike 3: validate 0 errors, `search` finds the topic, `--dense` and `--json` (`docs.detail`) work.
- **The agent block:** the integration's `agentDocs.append`. `astryx init --features agents` writes one
  managed block into `AGENTS.md`, and twice leaves one block (spike 3). It does not write `CLAUDE.md`;
  wiring a child's root (`AGENTS.md`, and a `CLAUDE.md` line that imports it) is story S9.
- **Fail closed:** the CLI prints some errors with exit 0. `scripts/ui.sh` fails on a non-zero exit, a first
  `Error:` line on either stream, or a `--json` envelope with `error` or an `ERR_*` code.
- **Upgrades:** bump both pins together, rerun the `ui-cli` CI job, read the upstream release notes.

## One doc, words per platform (story #228, 9 Nov 2026)

- **Problem:** a shared doc (Android and iOS) had one `usage` text, written for Compose. The `ios-bottomsheet` topic told
  a Swift reader to call `rememberModalBottomSheetState`. Props sat only under `platforms.android`, so iOS topics had none.
- **Decision:** the doc gains one optional field, `platformUsage: {android?, ios?, web?}`. Each entry has the same
  fields as upstream's `UsageDoc`: `description`, `bestPractices`, `accessibility`. `usage` keeps only words that fit
  every platform. A platform's topic is `usage` plus its own entry. Props come from `core` or that platform only.
- **Why not two docs:** one doc keeps one name, one contract and one coverage row per component (story #216). Only
  the words differ, so only the words split.
- **Why not shared words only:** some advice is about one platform's API (a state holder, a modifier). It must exist,
  and it must reach only that platform.
- **Guard:** `scripts/ui_topics.py` fails, naming the topic and the word, when a topic holds a name from the other
  platform. The one list is `OTHER_API` in that script, for example `remember…`, `Modifier.`, `16dp` for iOS,
  and `SwiftUI`, `@State`, `$isOn` for Android. Shared text names a token (like `feel.touchTarget`), never one
  platform's number, so no line needs an exception (PR #230 review).
- **iOS words** come from Apple's SwiftUI docs and HIG only (Tier A).

## The full API lists (story #231, 9 Nov 2026; reviews of PR #233)

- **Decision:** the coverage source is each library's own public API, not a design page. `scripts/ui_api_lists.py`
  writes `docs/research/android-m3-api.md` (Compose Material 3 1.4.0, `current.txt` at a fixed AOSP commit) and
  `docs/research/ios-swiftui-api.md` (Apple's SwiftUI documentation JSON). Each list pins its saved extracts by sha256.
- **Nothing is left out** (owner: "mujhe sab chahiye"). Every public top-level class and composable, every composable
  inside a `*Defaults` object, every View type and every View modifier is a row. A deprecated entry, or one Apple does
  not offer on iOS, is a row with a `status` (`deprecated` or `unavailable-ios`), the exact data field it came from,
  and its replacement: the vendor's own words for `deprecated`, our chosen iOS alternative for `unavailable-ios`.
  SwiftUI types that only hold views together keep category `plumbing`.
- **Doc fields:** `platformApi: {android?, ios?, web?}` with `family` (a family row), `variants` (objects
  `{name, note}` or `{name, props}`) and `supporting` (objects `{name, use}`). Each item, and the doc itself, may carry
  `status` with a required `replacement`. Plain strings are refused. Topics print a status item only as
  "Do not use: <name>. Use <replacement>."
- **Gate:** a row is covered only by a structured field of exactly one doc. A name the list does not have fails, and
  two docs claiming one row fails. The uncovered rows print as GAP lines and fail only with `--strict-api`, which
  stays off in CI until the family docs land, PR by PR. The last family PR turns it on. The gate has no exclusion list.
  Done on 9 Nov 2026: every Android and iOS row and every framework topic has its doc, so CI (job `ui-cli`) and
  `scripts/check_local.sh` run `check_ui_coverage.py --strict-api`. A new pin that adds API fails until it is documented.
- **Own family, own kind** (PR #255 review 2, 9 Nov 2026): on Android a component row is covered only by a doc of its
  own family, through its main API or its variants. A doc's family is the family of the row its `platforms.android`
  names, or its `platformApi.android.family`. So `Icon` listed as a variant in the Scaffold doc is a GAP, not a cover.
  Each slot names rows of its own kind only: a `supporting` entry that names a variant row fails.
- **The API list is the source of truth for Android** (same review): a doc whose `platforms.android` is a component row
  of `android-m3-api.md` is not an "extra". The 30-card list (`android-m3-components.md`) is still checked, so every
  card has its doc and topic, but it is no longer a cap on how many Android docs there are. iOS keeps its card list
  as the cap until the iOS lane decides the same.
- **iOS has the own-family rule too** (story #285, 9 Nov 2026): an iOS component or modifier row is covered only by
  a doc of its doc family. The generated `ios-swiftui-api.md` has a `Doc family` column. It is the row's Family (a
  type's own family, or a modifier's Apple page, such as Presentation modifiers), unless `IOS_DOC_FAMILY` in
  `scripts/ui_api_lists.py` maps the row to the doc of the control it changes (`.sheet` to BottomSheet, `.buttonStyle`
  to Button) or to the doc that groups it (Capsule to Shape). A doc's families are the Doc family of its
  `platforms.ios` row and its `platformApi.ios.family`, as on Android. On iOS the family is a label, not a row: it must
  be a Doc family of some row, and two docs cannot set the same one. Each modifier doc takes its Apple page as its
  family (PresentationModifiers is "Presentation modifiers", swift-charts is "Chart view modifiers"). So a swift-charts
  doc that claims `buttonStyle` is a GAP, and a doc moves a row only by an edit to the protected generator.
  Review 2 of PR #294 moved eight rows to the doc of their meaning: the confirmation dialogs and `fullScreenCover` to
  Dialog, `statusBarHidden` and `Color` to Appearance, `ButtonBorderShape` to Button, `scrollDismissesKeyboard` to
  ScrollView, `DocumentLaunchView` to its own doc, and `Canvas` to its own doc that says "Do not use" (rule 38).
- **The ceiling:** the map guards only the rows it names. The catch-all docs (InputModifiers holds 105 input and event
  modifiers, TechnologyModifiers 77, PresentationModifiers 42, AccessibilityModifiers and AppearanceModifiers 41 each,
  GraphicsModifiers 38) hold the rest under their own Apple page, so a row can sit in the wrong catch-all and the gate
  cannot tell. Story #296 is to split the catch-all docs by control, one catch-all per PR.
- **Framework names are checked too** (story #288, 9 Nov 2026): a framework doc (widgets, notifications, Swift Charts
  and the rest) names its framework's own types, which are no row of the two API lists. Each such name must be in
  `docs/research/sources/framework-names.json`, the saved public names of each package, or the gate fails. So a typo
  fails. `python3 scripts/ui_api_lists.py --fetch-frameworks` writes the file and its sha256 pin in
  `framework-topics.md`; the gate fails when the file does not match its pin. A doc name matches a saved name when it
  is that name or its end after a dot (`NotificationCompat.Builder` matches `androidx.core.app.NotificationCompat.Builder`).
  A bare name must be type-cased (its last segment starts with an uppercase letter), so a fragment such as
  `permission` fails; a function such as `updateAll` is written qualified (`androidx.glance.appwidget.updateAll`).
  The sha256 pin catches mistakes, not tampering: whoever edits the names file can edit the pin line beside it. The
  diff review is the guard, which is why `ui_api_lists.py` is a protected path and the file is regenerated by the
  script, never by hand.
  Sources, all Tier A: Glance 1.2.0 and Core 1.19.1 `api/current.txt` at their release commits, the Android 16
  platform `api/current.txt` (tag `android-16.0.0_r1`, API level 36), and Apple's documentation JSON.
- **The limit:** the list holds what the docs name today, not every name of every package. Android keeps all of
  Glance, `androidx.core.app`, `android.app` and `android.Manifest`. Apple keeps the symbols linked from chosen seed
  pages and the topic pages two levels below them (all of Charts, HealthKitUI, UserNotifications and App Intents, part
  of UIKit, WebKit and WidgetKit). A real name that is not saved yet also fails; add its page to `APPLE_PACKAGES` or
  `ANDROID_PACKAGES` in `scripts/ui_api_lists.py` and fetch again. A name of the other platform fails too.

## The compile proof (story #217, 9 Nov 2026; owner yes on #217: "haan")
- **Decision:** CI compiles every template and a generated proof of every contract prop. `scripts/ui_proof.py` writes
  `ui/android/proof/ApiProof.kt` and `ui/ios/proof/ApiProof.swift` from the contracts; `--check` fails when they are stale.
  Job `ui-android-compile` builds `ui/android` with Gradle 8.14.3, AGP 8.13.2, Kotlin 2.2.21 (and its Compose compiler
  plugin) and Compose BOM 2025.10.00 (material3 1.4.0). Job `ui-ios-compile` runs `xcodebuild` for generic iOS on Xcode 16.4.
- CI checks that the Kotlin and Swift compile. It does not run them. Both jobs run only when `ui/**` changes.
- All downloads happen on GitHub's runners. Nothing is installed on the owner's Mac.
- The Gradle zip is fetched with `curl` and checked with `sha256sum -c` against `distributionSha256Sum` in
  `gradle-wrapper.properties` before the build (review 2 of PR #291). No action downloads Gradle behind that check.
- The proof has limits: a spec `v` override is not type-proved, and a Kotlin `{}` lambda does not prove arity.
