# ADR-023: A feature PR goes into the train and runs light CI; the train PR runs everything

Date: 2026-11-20
Status: Accepted (owner, "Rasta B", 20 Nov 2026, story #592)

## Context

Every PR ran all jobs of `ci.yml`: the full test suite, two Android jobs and three iOS jobs on macos-15. macOS machines are often not free, so approved work waited many times a day. The team already lands work as a train: approved PRs are merged with plain git into `train/<date>`, and that one PR goes into `dev`.

## Decision

1. A **light run** is a pull request whose base branch starts with `train/`. Every other run is a **full run**. The one condition, the same text everywhere, is `github.event_name == 'pull_request' && startsWith(github.base_ref, 'train/')`. It reads the base branch only, never the head branch.
2. The six heavy jobs (`test`, `ui-android-compile`, `ui-android-lint`, `ui-ios-compile`, `ui-ios-lint`, `ui-ios-snapshots`) have a job-level `if:` that is false on a light run. The phone jobs keep their change-map test. No job leaves the `needs:` of `gate`.
3. The `gate` job keeps `if: always()` and its failed-or-cancelled check. On a light run it skips the change-map step and prints `light run: the heavy jobs did not run; they run on the train pull request into dev`. On a full run the result of `test` must be `success`; a skipped `test` fails the gate.

## What stays safe

- Nothing reaches `dev` on light CI: the only way into `dev` is a PR into `dev`, which is always a full run.
- A branch named `train/x` used as a head gets no light run. A PR whose base changes from a train to `dev` gets a new full run. An empty or odd value counts as full.
- If the condition is missing in a heavy job on a full run, `test` fails the gate, and the change map fails a phone job whose area is on. If it is missing in the gate, a light run fails the gate.
- Cheap Linux checks, `checks.yml`, `review_merge.sh` and the change map are not changed.
- On a light run the gate job is named `gate-light`, on a full run `gate`. `dev`'s branch protection requires a check named exactly `gate`, and GitHub reads checks by commit, so a light result must never carry that name: a second PR with the same head into `dev` could otherwise look mergeable.
- The same class is wider: a PR picks its own base. So `gate` is the name only on a non-PR run or a PR into exactly `dev` or `main`; a PR into a `train/` base is `gate-light`; a PR into any other base, or with an empty base, is `gate-other`. Its jobs run as before; only the name of the check changes, and `review_merge.sh`, `release.sh` and the nightly run look for `gate`, so they ignore a `gate-other` result (story #601).

## What gets weaker

- A feature PR that breaks a test or a phone build is found at train time, not before. The coder runs `scripts/check_local.sh` and `scripts/check_local.sh tests` on the Mac before a push.
- A train branch is not protected. It was not before either: the train is built with plain git.

## How to undo

Revert this PR. No GitHub setting changes.
