# ADR-010: Where the mode lives, once an agent could try to flip it

Date: 2026-10-31
Status: Accepted

## Context

Story #131 hardened the merge gate so a pull request can no longer loosen its own rules. That raised
the question the issue for story #140 asked directly: the mode itself (`manual`/`semi`/`auto`) still
lived in an **untracked** file (`$(git rev-parse --git-common-dir)/shipquick-mode`). Nothing stopped an
agent's own `Bash` tool call from writing `auto` into that file and then merging through the gate on
its own — the file was never part of the repository, so no PR, no review, and no CI ever saw the
change. Three ways to close that gap were on the table:

- **(a) A tracked file in the repo** (`.shipquick/mode`), listed in `scripts/protected_paths.txt`.
  Changing it needs a PR that touches a protected path, so `scripts/review_merge.sh` refuses to merge
  it in Auto ("protected path, owner merges") and only the owner's own merge in the GitHub UI can move
  it. The file's whole history is `git log`.
- **(b) A GitHub repository variable or environment**, read through `gh api` at session start. This
  moves the value out of the working tree entirely, so an agent's local `Bash` call cannot touch it no
  matter what. But writing or reading a repository variable is itself a GitHub-permissions action, and
  probing this (during the story #131 session) was blocked outright by the coding tool's own "Modify
  Shared Resources" permission classifier — the harness treats changing shared GitHub settings as a
  risk class it will not let an agent attempt at all, confirming the owner's instinct that this is the
  kind of action that should need his own hands on it anyway.
- **(c) A signed or encrypted file** only the owner's key could write. Closes the gap the same way as
  (a) but needs a key-management story (generation, rotation, where the private half lives) that no
  other ShipQuick mechanism needs yet, for no stronger a guarantee than (a) already gives once (a) is
  a protected path.

## Decision

**Option (a).** `scripts/mode.sh get` reads `.shipquick/mode` first when it exists, and only falls back
to the old untracked file when it does not — so a project adopts the new mechanism the instant the
owner merges the one PR that creates it, with nothing else to migrate first. `mode.sh set` refuses
outright once `.shipquick/mode` exists, telling the owner to edit the file and open a PR instead.

Why (a) over (b): the blocked probe during story #131 is itself evidence, not a workaround to route
around — a mechanism this project cannot even test from inside an agent session is not one to depend
on for every project's gate. (a) also needs nothing a child project doesn't already have (git, a PR,
the protected-paths list from story #131), while (b) would need a GitHub token scope and an API call
most child projects have no other reason to carry.

Why (a) over (c): (a) already gets the only property that matters here — an agent's own tool calls
cannot write the file that controls the gate — from a mechanism (protected paths) story #131 had
already built and proven. (c) buys no extra safety over that and costs a key-management story on top.

## Consequences

Good:

- The mode's whole history is now `git log .shipquick/mode` — who set Auto, when, in which PR — instead
  of a value that lived only on one machine's disk with no record.
- No new dependency, no new permission scope, no key to lose. Every project that has story #131's
  protected-paths mechanism already has everything this needs.
- The switch is live per-project the moment that project's owner merges the file in; nothing blocks on
  every project moving at once.

Bad and to watch:

- A project with no `.shipquick/mode` yet is still exactly as exposed as before this story, until its
  owner does that one merge. This ADR does not retrofit existing projects; `scripts/adoption_scan.py`
  (story #124) is the mechanism that could be extended to flag a project still on the untracked file,
  if that turns out to matter — not done here, out of this story's scope.
- `.shipquick/mode` is one word for the whole project; it does not yet distinguish "Auto for the dev
  branch" from "Auto for main," and does not need to given today's one-mode-per-project rule.
