# ADR-009: Provenance, not recency, decides a Production board vs app disagreement

Date: 2026-10-30
Status: Accepted

## Context

Story #125, raised by GoServe (feedback issue #125): a drift audit used recency to decide whether a
Production board or the live app was right. It read 62 of 66 boards as "stale" and rewrote approved
design to match code nobody had approved — the opposite of rule 2 (design first, approval, then code),
which exists precisely so code never gets ahead of an approved board.

## Decision

- If no approved board covers an app change, **the app is the drift and the board stands.** The fix is
  a code story back to the board, or a new design story through approval — never a board rewrite from
  whatever the app happens to do.
- A Production board is rewritten from the app only when the PR that changed the app named that
  approved board (`Design board: <name>` and `Approved: <date>`, rule 2 / story #121).
- The manifest `scripts/canvas_stage.py` reads carries this directly: a `boards` entry in the section
  whose id is `"production"` must be `{"board": "<name>", "pr": "<PR>", "approved": "<date>"}`, not a
  plain filename. The tool refuses to lay out — and writes nothing — when that provenance is missing,
  the same way it already refuses an overlap or a box outside its section (ADR for story #105).
- A drift audit (`docs/templates/drift-report.md`) lists every mismatch — board, app screen, the PR
  that caused it, whether that PR named an approved board, and the verdict (app drift or board drift)
  — and never edits a board itself. Only a human decision, acting on that list, changes anything.

## Consequences

Good:

- Design approval cannot be silently overwritten by an audit that only looked at timestamps.
- The refusal is enforced the same way every other canvas rule is: declaratively, in the manifest, by
  the one tool that writes the canvas — not by a convention someone has to remember to follow.

Bad and to watch:

- Every Production board now needs its PR and approval date carried forward in the manifest by hand
  when it is first adopted into Production; a project migrating an existing canvas must backfill this
  once (there is no way to infer a PR for a board already in Production before story #125).
- The drift report is still a manual exercise (a human reads board vs. app and fills the table); it is
  not run by a script. Automating "does this app screen match this board" is future work, not this
  story's scope.
