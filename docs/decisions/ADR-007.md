# ADR-007: Design is checked before code, not after

Date: 2026-10-30
Status: Accepted

Note: numbered 007 rather than the next free slot (006) on `dev` at branch time, because story #120
(PR #122) also claims ADR-006 and was opened first. Renumber at merge time if that guess is wrong.

## Context

Story #121: `docs/DESIGN_PROCESS.md` rule 2 said a UI change lands on the canvas "in the same story
as the code" — same PR, no ordering between them. In practice this let code ship ahead of an
approved design: a screen could be built, then a board added after the fact to satisfy the rule,
with the canvas and the app drifting apart whenever the "after" board differed from what shipped.

## Decision

- Rule 2 is rewritten: design first, approval, then code. Every story asks at Definition of Ready
  whether it touches the frontend; a "yes" needs a sample screen on the canvas, shown to and
  approved by the owner (board moved to "Design final not live"), before any code starts. The code
  then builds that exact screen, copy word for word.
- The story issue template (`user-story.yml`) gets a required `Frontend change: yes / no` field,
  plus `Design board:` and `Approved:` inputs required when the answer is yes.
- `scripts/check_frontend_design.sh` reads a project's own `docs/frontend-paths.txt` (one shell glob
  per line; nothing configured means nothing is checked) and fails a PR that touches one of those
  paths with no `Design board: <name>` line in its body, or that claims "no screen change" while
  still touching them. It runs as a CI job (`frontend-design`, every PR) and as a `check_local.sh`
  check (scanning the commit log since the branch's base, since a PR body does not exist yet before
  a push).
- D5 (Ready) gets the `Frontend change` item; D6 (Done) is reworded so the board named in the PR is
  the one already approved before the code, not one added after.

## Consequences

Good:

- The canvas can no longer drift behind the code: a frontend PR cannot merge without naming an
  already-approved board.
- The same shape (globs file, generic script) works for any project; ShipQuick itself has no
  `docs/frontend-paths.txt`, so the check is always a no-op skip there.

Bad and to watch:

- The check only proves a board was *named*, not that the code actually matches it — that is still
  the reviewer's job (rule 2's "copy word for word" line), same as before this story.
- A project with a loosely-written globs file (too broad) will demand a board for files that are not
  really UI; too narrow, and a real screen change slips through unchecked. The globs file is the
  project's own judgment call, not ShipQuick's.
