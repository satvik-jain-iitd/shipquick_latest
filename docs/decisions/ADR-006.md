# ADR-006: A dev -> main promotion is gated on a followable, fully-ticked UAT checklist

Date: 2026-10-30
Status: Accepted

## Context

Story #120: every project needs two live links, dev and production, so the owner tests by hand
before real users see a change. Without a gate, a promotion PR (`dev -> main`) could merge the
same way any other PR does — on green CI and a reviewer approval — and reach production without
the owner ever having looked at the dev link. In auto mode this risk is higher: the reviewer
session approves and merges without asking the owner anything else.

A first version of this gate (this ADR's earlier draft) checked for a "tested on dev" comment
from the reviewer account. The owner rejected it: a one-line comment proves nothing about what was
actually tested, and does not force the coder to say what "tested" even means for this release.

## Decision

- The `dev -> main` PR body carries a `## UAT on dev (<dev link>)` section (template:
  `docs/templates/uat-checklist.md`): one checkbox per story in the release, plus "Old flows still
  work", "Design matches the approved boards", and a `Known bugs going to production:` line.
- Every story line must be followable by a new user who has never seen the app: the exact link or
  screen, the test data to use, numbered one-action steps, and an **Expected:** line with exact
  text where there is text.
- `scripts/check_uat.py` validates the shape of that section (every story line has an Open:, steps,
  and an Expected: line; both fixed lines and the Known-bugs line are present). It is used both as
  a CI check on the PR and inside `review_merge.sh`.
- `scripts/review_merge.sh` adds one check, only when a PR's base branch is `main`: the section
  must exist, pass `check_uat.py`, and have no unticked box (`- [ ]`) left in it. The owner ticks
  every box on the dev link itself, then approves.
- This runs in every mode, including auto, because the risk (an untested change reaching
  production) is the same in every mode.
- `scripts/check_environments.sh` and `scripts/env_drift.sh` are the supporting checks: the first
  keeps both links visible in the project's own `CLAUDE.md` once it is past milestone D0; the
  second reports drift between the two branches after a promotion. Neither blocks a merge by
  itself — the UAT checklist is the one hard stop before production.

## Consequences

Good:

- No promotion to `main` merges — in any mode — with an unticked box or an unfollowable story line.
- A new user, not just the owner, could run the checklist: the shape forces exact links, exact
  data, and exact expected text, not "looks fine".
- `docs/ENVIRONMENTS.md` gives a generic rule plus one worked example per host type, so a new
  project does not have to invent its own dev/production split.

Bad and to watch:

- Writing a good checklist line takes real effort from the coder; a rushed line that is technically
  "followable" (has all three parts) can still be vague. `check_uat.py` checks shape, not quality.
- `env_drift.sh` is a report, not a gate. A promotion that merges cleanly but later drifts (a
  hotfix on `main` outside the normal flow) is still possible; nothing here stops that.
