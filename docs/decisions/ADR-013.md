# ADR-013: A protected PR merges after a second review and the owner's yes

Date: 2026-11-09
Status: Proposed (story #180, S0 of the Library first plan)

## Context

Story #131 made every protected PR (CI config, lint baselines, gate scripts) an owner-only merge.
That kept a gate from loosening itself. But it also put every such PR in the owner's queue, even
small fixes the reviewer had already checked. On 9 Nov 2026 five protected PRs waited on him at once.

The owner's rule (Library first plan, 9 Nov 2026): a protected PR gets the reviewer's review,
then a fresh second-reviewer agent, then the owner's one-line yes. Then the reviewer merges it.

## Decision

`scripts/review_merge.sh` lets a protected PR through only when the approving review on the head
commit carries both lines:

- `Second review: <who, findings>`: a fresh reviewer agent read the diff cold.
- `Owner yes: <YYYY-MM-DD> "<his words>"`: the owner's own words, quoted, with the date.

The lines count only in the approving review, never in the PR body. The coder writes the body, so
the coder could type them there.

One exception stays: a PR that touches `.shipquick/*` (mode, roles, freeze) is the owner's own
merge, whatever the review says. Those files decide who may merge at all.

## What this does not stop

The reviewer and the owner share one GitHub account. So the `Owner yes:` line is recorded by the
reviewer, not signed by the owner. It is an audit line, not proof. A reviewer that types a yes the
owner never gave passes. The quoted words and the date make a false line easy to spot later.

## Consequences

- The owner no longer clicks merge on protected PRs. He gives a one-line yes in chat.
- The reviewer must run a fresh second-review agent on every protected PR and name its result.
- `docs/MODES.md` and `docs/PR_RULES.md` name the two lines.
