# Sprint Planning

How to plan a one-week sprint.

## What a sprint is

One week. One GitHub milestone. A small set of Refined stories.

## Capacity

Do not count hours. Count **review bandwidth**.
The owner can review a small number of stories per week.
Start with 3 to 5 stories. Adjust after each retro.

## Steps

1. Create the milestone. Name it `S<nn>` (for example `S01`). Set the due date to the sprint end.
2. Open the board. Look at the **Refined** column.
3. Pick the top items by priority (see `PRIORITIZATION.md`).
4. Fit them to the review bandwidth. Do not overfill.
5. Write the **sprint goal**: one sentence. What is true at the end?
6. Move the chosen issues to **Sprint Ready**. Assign the milestone.
7. Copy `templates/sprint-plan.md` into `sprints/S<nn>/plan.md`. Fill it in.
8. Announce the goal. Start.

## Sprint goal

One sentence. Example: "A user can sign up, log in, and see their dashboard."

If the goal cannot be written, the sprint is not ready.

## During the sprint

- Check the board each day. 5 minutes.
- Keep **In Progress** to a max of 2.
- Clear `blocked` items immediately.
- If a story cannot finish, move it to the next sprint. Do not rush it.

## Scope change

Do not add new work mid-sprint unless it is urgent.
Urgent work goes to the next sprint unless it is a production bug.
