# shipquick_latest: Project Rules

Read first: `docs/PLAN.md` (the plan and case study) and `docs/process-trace.md`.

Standing rules, every session. This file is the whole protocol and holds no project facts. Stack, folders and ADR pointers go in the project's own CLAUDE.md, started from `docs/CLAUDE.project.template.md`. Rule numbers never change, so 6, 9 and 10 stay free.
0. **Mode** (owner, 26 Oct 2026). At session start run `scripts/mode.sh get` (in a child project: `knowledge/shipquick_latest/scripts/mode.sh get`). If it exits 3 the mode is not set: ask the owner (Manual, Semi or Auto); the owner sets it with `! bash scripts/mode.sh set <word>` typed himself, and an agent never runs set. In Auto an agent merges only with `scripts/review_merge.sh <pr>`. Details: `docs/MODES.md`.
1. First action: read `docs/process-trace.md`. Last action before "done": append this session's steps to it (one row each: date, step, actor, what, artifact, owner contact asked / volunteered / reviewed). A new row writes `-` in the `#` column, so two branches that add rows at once never collide on a number; old rows keep theirs.
2. Every owner message that changes direction gets bullets in `docs/discussions/<START_DATE>.md`.
3. Every idea the owner states is logged at once with `~/Desktop/SecondBrain/tools/idea.py` and one line in `docs/ideas.md`.
4. Work only from GitHub issues. Branch `feat/<issue>-<slug>` from `dev`. PR feat -> dev (self-review checklist, CI green). PR dev -> main at each demo increment. The coder opens every PR, dev -> main too; the reviewer never opens one. Who merges main depends on the mode: in manual and semi the owner merges it; in auto the reviewer merges it with `scripts/review_merge.sh` and the owner is not asked (`docs/MODES.md`).
5. TDD: failing test first, named after the Gherkin scenario, failure pasted in the PR. Tests listed in `docs/tests/test-cases.md`.
7. Definition of Ready before a story starts; Definition of Done before it closes (docs/PLAN.md Part D).
8. Decisions that change architecture or scope get `docs/decisions/ADR-NNN.md` in the same PR.
11. Branches: `main` is protected, never push direct. `dev` is integration. Feature branches `feat/<issue>-<slug>` come from `dev`, merge back via PR.
12. PRs stay small: max 50 files. Commits follow `COMMIT_GUIDELINES.md`. Merge only when all gates pass: green CI, one approval (not the author), zero unresolved comments, branch up to date, not a Draft, issue linked with `Closes #N`. `Closes #N` only auto-closes on a merge into `main`. After a merge into `dev`, run `python3 scripts/close_linked_issues.py <pr>` (dry run, then `--yes` after one owner yes); it closes only linked story issues, never epics, never for an open or unmerged PR. Full rules in `docs/PR_RULES.md`. Coverage tracked in `docs/PR_COVERAGE.md`.
13. Pre-commit runs on every commit: no secrets, no files over 500KB, no merge markers, markdown blocks closed.
14. Branch prefixes: `feat/` features, `fix/` bugs, `docs/` docs, `design/` design system, `test/` tests, `chore/` maintenance, `ci/` pipelines. Design changes get `docs/decisions/ADR-NNN.md` in the same PR.
15. One bug = one issue. Never club unrelated bugs. Every bug gets severity + user story + owner + milestone before any fix work.
16. Triage before fixing: read, assign severity, link user story, assign owner, add `triaged`, move on board. Update `docs/bugs/ACTIVE_BUGS.md` on every status change.
17. Every issue and PR gets a milestone (D0-D6) and an assignee. Demo artifacts stay labeled and closed; they are placeholders, not real work.
18. PM and agile process lives in `pm/agile/`. A sprint is one week and one GitHub milestone (`S<nn>`). A PI is a D increment (an epic). Rank work by value only, never hours or story points. Size is T-shirt only (`XS, S, M, L, XL`). Write the sprint plan, review, and retro in `pm/agile/sprints/S<nn>/`. Versions use SemVer `vX.Y.Z`.
19. Teammate blocks: a unit of work is anything you finish that another teammate must act on or know about. When you finish one, end your reply with one fenced block per other teammate (`To <role>, from <role>, re <ref>:`, roles from `docs/TEAM_ROSTER.md`, any stable ref, English, under 120 words, numbered, last line `Need from you: ...` or `Nothing needed from you.`). Sessions on the same Mac send them directly with `SendMessage` (rule 27); otherwise the owner relays them unchanged. A block to the owner is an ordered to-do: every line starts with `Now:`, `After <event>:` or `Not yet:`, and one `Merge:` line says now, not yet, or nothing to merge; the owner merges exactly once, right after the reviewer's approve block. The coder's block to the reviewer lives in the PR body under `## For the reviewer` and CI checks it (`scripts/check_block.py`); the reviewer's block to the coder is the review body. Full rule: `docs/TEAM_PROTOCOL.md`.
20. **Radar first** (owner, 25 Oct 2026, the strictest rule). Before any new component, script, skill, workflow or tool: run the `radar` skill on the need, read the top 3 READMEs, record the run in `docs/research/repo-radar.md`, reuse or borrow first. Build from scratch only when the run found nothing, and say so. No radar run, no new code.
21. **Live roadmap from the first epic** (owner, 25 Oct 2026). Every project has one live page generated from its issues and PRs, never edited by hand. It runs on GitHub Actions alone (a reusable workflow, `ROADMAP.md` on a `roadmap` branch), no n8n and no other tool, so a kit user needs nothing extra. Requirement and setup: `docs/LIVE_ROADMAP.md`.
22. **Two GitHub accounts** (owner, 13 Oct 2026; review rule 26 Oct 2026). The build account (`klickbae8yt-star`) makes every commit, push and PR. The review account (`satvik-jain-iitd`) reviews: the reviewer session comments, requests changes and approves with it. The owner merges in the GitHub UI. No agent merges unless the owner asks for that one merge. Nobody pushes as the review account.
23. **Up to 3 stacks open, in separate lanes** (owner, 26 Oct 2026; before: one stack, 22 Oct 2026). A stack is one PR or a chain of stacked PRs (`gh stack`; bottom layer targets `dev`). A lane is a set of stories that touch the same files: they share one lane and run in order, and foundation work (shared types, API shape, tables) merges first. Different lanes run at the same time, each with its own coder session and git worktree. Plan the lanes in the sprint plan with `pm/agile/templates/sprint-lanes.md`. Run `gh pr list --state open` before pushing a new branch: one open stack per lane, up to 3 lanes. Work that depends on an open PR is a layer on top of it. Merge bottom first; never merge a layer above an unapproved one. To keep conflicts few: merge `dev` into every open branch once a day, with Git on the Mac, and right before the merge, merge `dev` once more with Git on the Mac if `dev` moved (GitHub's own button shows CONFLICTING otherwise). Keep the append-only logs (`docs/process-trace.md`, `docs/LEARNINGS.md`) as they are: rows are only added at the end, never edited (`.gitattributes` sets `merge=union`). `docs/ideas.md` is not on that list because its rows get status edits.
24. **`main` holds only run-critical code** (owner, 13 Oct 2026) in projects that deploy from `main`. Docs, plans, decisions and rules live on `dev`. Promote with a release branch that takes only the run paths.
25. **Phase gate** (owner, 2026). Before a new MVP phase starts, run a question-and-answer with the owner on every infrastructure item for that phase, research the gaps, set up with his yes, and record it. Nothing in the phase is built before the gate passes.
26. **Nothing stays tacit**. Every assumption goes in `docs/assumptions.md`; every follow-up in `docs/follow-ups.md`; every learning or mistake gets a row in `docs/LEARNINGS.md`.
27. **The two-session pair** (owner, 26 Oct 2026). A project can run a coder session (Sonnet, named `<project>-dev`) and a reviewer and orchestrator session (Opus, named `<project>-qa`). They talk directly with `ListAgents` and `SendMessage`, in teammate-block shape. Each session works in its own folder (the reviewer in a git worktree) and never edits the other's folder. The coder opens every PR; the reviewer never opens a PR, it only reviews and merges (rule 4). Roles: `docs/TEAM_ROSTER.md`.
28. **Runtime rule** (owner, 26 Oct 2026). Everything runs free first and on n8n on Oracle first, set up in n8n. Nothing runs from the owner's Mac unless a login, cookies or a burner account force it. Test local model quality before picking a model.
29. **Useful checks only** (owner, 26 Oct 2026). Every CI check protects this project or it is removed. Every CI check also runs locally before a push (`scripts/check_local.sh`). Must-have set: `docs/research/ci-checks.md`.
30. **The review loop** (owner, 26 Oct 2026). The reviewer leaves comments on every changed file (inline, on the lines that matter, plus one summary). The coder answers each thread and fixes or explains. They go back and forth until they agree; only the reviewer resolves a thread. The author never reviews their own PR: when the reviewer session writes a PR, the coder session reviews it. Merge needs zero unresolved threads (`docs/PR_RULES.md`).
31. **Design process** (owner, 29 Oct 2026; extended 30 Oct 2026, story #121). Read `docs/DESIGN_PROCESS.md` before any screen, frame or canvas work: direction in two or three frames first, design first and approved before any code (a sample screen on the canvas, from the latest approved board, shown to the owner; code starts only after he approves it and the board moves to "Design final not live"), the canvas by stage from a manifest with background boards, contrast checked wherever text is placed, nothing outside its board, the owner's design feedback written there the same day. Every story answers `Frontend change: yes / no` at Ready; a "yes" needs `Design board:` and `Approved:` filled before it leaves Ready. A PR touching a project's own frontend paths must name that board in its body or `scripts/check_frontend_design.sh` fails it (CI and `scripts/check_local.sh`).
32. **Model load** (owner, 29 Oct 2026). Every model job is split into micro tasks sized to the model (one label, one yes or no, one field, one sentence per call). The smallest model that runs fast on the project's own run box goes first and steps up only when a written eval fails, against that box's measured ceiling. A speed estimate starts at a measured factor of any published number (one third until measured) until a real run on the box replaces it. Target speed with workable accuracy first, then fine-tune on the project's own data. A big call goes to the project's free-tier model only occasionally, under a day budget that is a fixed share of the vendor's cap. No model verdict without the matrix: the prompt techniques and the micro-task breakdowns of `docs/research/prompt-techniques.md` are tried on the smallest model first, pre-registered, before any "model X is best". Every call site is listed in `docs/data/model-calls.md` and checked with `scripts/model_calls.sh --check`. Full rules and the project's own worked example: `docs/MODEL_LOAD.md`.
33. **The ShipQuick inbox** (owner, 30 Oct 2026). A child project hitting a ShipQuick gap mid-task never opens a full PR here itself: say "send this to ShipQuick" for the `shipquick-feedback` skill (install once with `knowledge/shipquick_latest/scripts/install_skill.sh`), or by hand fill `docs/templates/feedback.md` (nine required sections: situation, expected vs seen, steps to reproduce, impact, root cause as a five-whys chain with at least three "Why" lines, why ShipQuick did not catch it, how big teams avoid it, generic fix, stop the repeat) and run `knowledge/shipquick_latest/scripts/feedback.sh --title "<t>" --body-file <f> [--new]` from its own repo. A missing, empty, or too-short section refuses and names it; nothing opens. The script fills the header itself (project, ShipQuick commit, date). A similar open `feedback` issue gets a comment instead of a new one (`--new` forces a new one). Target repo (`$SHIPQUICK_REPO`) and build account (`$SHIPQUICK_BUILD_USER`) are overridable. No gh login: prints the title and the full body and exits 1, nothing lost. The ShipQuick coder session turns a `feedback` issue into a proper story; the reviewer reviews and merges it like any other. Full rule: `docs/FEEDBACK.md`.
