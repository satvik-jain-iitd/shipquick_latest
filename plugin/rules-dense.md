# ShipQuick rules (dense, generated from CLAUDE.md)

Read these every session. Full text: CLAUDE.md. Do not edit this file; run plugin/gen_rules_dense.py.

- Rule 0: Mode (owner, 26 Oct 2026). At session start run scripts/mode.sh get (in a child project: knowledge/shipquick_latest/scripts/mode.sh get). If it exits 3 the mode is not set: ask the owner (Manual, Semi or Auto); the owner sets it with ! bash scripts/mode.sh set <word> typed himself, and an agent never runs set. In Auto an agent merges only with scripts/review_merge.sh <pr>. Details: docs/MODES.md.
- Rule 1: First action: read docs/process-trace.md. Last action before "done": append this session's steps to it (one row each: date, step, actor, what, artifact, owner contact asked / volunteered / reviewed). A new row writes - in the # column, so two branches that add rows at once never collide on a number; old rows keep theirs.
- Rule 4: Work only from GitHub issues. Branch feat/<issue>-<slug> from dev. PR feat -> dev (self-review checklist, CI green). PR dev -> main at each demo increment. The coder opens every PR, dev -> main too; the reviewer never opens one. Who merges main depends on the mode: in manual and semi the owner merges it; in auto the reviewer merges it with scripts/review_merge.sh and the owner is not asked (docs/MODES.md).
- Rule 5: TDD: failing test first, named after the Gherkin scenario, failure pasted in the PR. Tests listed in docs/tests/test-cases.md.
- Rule 12: PRs stay small: max 50 files. Commits follow COMMIT_GUIDELINES.md. Merge only when all gates pass: green CI, one approval (not the author), zero unresolved comments, branch up to date, not a Draft, issue linked with Closes #N. Closes #N only auto-closes on a merge into main. After a merge into dev, run python3 scripts/close_linked_issues.py <pr> (dry run, then --yes after one owner yes); it closes only linked story issues, never epics, never for an open or unmerged PR. Full rules in docs/PR_RULES.md. Coverage tracked in docs/PR_COVERAGE.md.
- Rule 19: Teammate blocks: a unit of work is anything you finish that another teammate must act on or know about. When you finish one, end your reply with one fenced block per other teammate (To <role>, from <role>, re <ref>:, roles from docs/TEAM_ROSTER.md, any stable ref, English, under 120 words, numbered, last line Need from you: ... or Nothing needed from you.). Sessions on the same Mac send them directly with SendMessage (rule 27); otherwise the owner relays them unchanged.
- Rule 20: Radar first (owner, 25 Oct 2026, the strictest rule). Before any new component, script, skill, workflow or tool: run the radar skill on the need, read the top 3 READMEs, record the run in docs/research/repo-radar.md, reuse or borrow first. Build from scratch only when the run found nothing, and say so. No radar run, no new code.
- Rule 22: Two GitHub accounts (owner, 13 Oct 2026; review rule 26 Oct 2026). The build account (klickbae8yt-star) makes every commit, push and PR. The review account (satvik-jain-iitd) reviews: the reviewer session comments, requests changes and approves with it. The owner merges in the GitHub UI. No agent merges unless the owner asks for that one merge. Nobody pushes as the review account.
- Rule 26: Nothing stays tacit. Every assumption goes in docs/assumptions.md; every follow-up in docs/follow-ups.md; every learning or mistake gets a row in docs/LEARNINGS.md.
- Rule 30: The review loop (owner, 26 Oct 2026). The reviewer leaves comments on every changed file (inline, on the lines that matter, plus one summary). The coder answers each thread and fixes or explains. They go back and forth until they agree; only the reviewer resolves a thread. On a frontend PR in a project with docs/screens.txt, the approval body says Render: <board> -- matches after the render was put beside the board, or scripts/review_merge.sh refuses (story #153, docs/SCREENS.md). The author never reviews their own PR: when the reviewer session writes a PR, the coder session reviews it. Merge needs zero unresolved threads (docs/PR_RULES.md).
